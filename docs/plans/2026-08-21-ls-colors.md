## In scope

GNU `ls` reads `LS_COLORS` (colon-separated `KEY=SGR` pairs)
when color is on. Keys include type codes (`di`, `ln`, `ex`,
`so`, `pi`, `bd`, `cd`, `or`, `mi`, `su`, `sg`, `tw`, `ow`,
`st`, `fi`, `no`) and suffix globs (`*.zip`). Values are SGR
parameter strings (`01;34`). Missing/empty `LS_COLORS` keeps
today's hardcoded vibeutils palette.

Add `src/common/ls_colors.zig` (force-imported, exported as
`common.ls_colors`):

- Parse `LS_COLORS` text into a table. Never `setenv` (issue
  #95). Tests use `env.test_overrides` or pass the string
  directly to the parser (prefer the pure parser).
- Type-code lookup and longest-suffix `*.ext` match.
- Invalid pairs skipped (GNU ignores junk); empty value means
  no color for that key.
- Hard cap on entries (e.g. 256) and on SGR length. No
  recursion. Two asserts per function, ≤70 lines.

`src/ls/display.zig` `getFileColor` / name styling: when color
is on and a parsed table is present, wrap the name with
`\x1b[{s}m` … reset from the matching key. If no key matches,
keep the current hardcoded kind/executable colors (do not go
colorless). `NO_COLOR` / `TERM=dumb` still win (existing
guards). `--color=never` still disables.

Do **not** implement `dircolors(1)`. Do not theme `df`/`du`
from `LS_COLORS`.

`CHANGELOG.md` Unreleased / Added. Check the Color Support
box. `man/man1/ls.1`: one sentence that `LS_COLORS` is
honored when color is on (GNU).

## Tests (failing first, separate test-writer)

Names without `#`. No privileged tests. Filter-stdin: ls
does not read stdin as a filter; unit tests must not hang.

Parser (`src/common/ls_colors.zig`):

1. Empty / missing string → no entries (lookup falls through).
2. `di=01;34` → directory key returns `01;34`.
3. `*.zip=01;31:di=01;34` → zip suffix and di both work.
4. Longest suffix wins (`*.tar.gz` over `*.gz` when both set).
5. Junk pair skipped; valid neighbor kept.
6. Cap: more than `ls_colors_entries_max` extra keys ignored
   (bounded loop).

ls (`src/ls/`, `env.test_overrides`, never setenv):

7. `LS_COLORS=di=01;34` with `--color=always` on a directory
   name emits `01;34` (or the CSI form the implementation
   chooses) and a reset. Skip or pin `TERM` if `TERM=dumb`
   in this environment; scrub `NO_COLOR` (`env -u NO_COLOR`)
   for integration.
8. `--color=never` plus `LS_COLORS` emits no CSI.
9. Unset `LS_COLORS` keeps today's bright-blue directory
   (characterization / sabotage if needed).

Integration: `tests/utilities/ls/` one case with
`LS_COLORS=di=01;34` and `--color=always`, `env -u NO_COLOR`,
`TERM=xterm-256color`.

Prove RED: (2)(3)(7) fail until the module exists / ls ignores
the env var. Test-writer stubs the parser so failures are
assertions, not compile errors.

## Risks

- Issue #95: never setenv. Pure parser + `test_overrides`.
- `TERM=dumb` / `NO_COLOR=1` in Cloud: pin TERM and scrub
  NO_COLOR for color tests (AGENTS.md).
- SGR injection: trust the OS / the env; do not try to
  "sanitize" user LS_COLORS beyond length caps (correctness,
  not security theater). Still bound the string so a huge
  env cannot blow the arena.
- macOS: `LS_COLORS` is GNU; BSD ls uses `LSCOLORS`. Follow
  GNU (CLAUDE.md). Do not parse `LSCOLORS` in this slice.
- Force-import `ls_colors.zig` alphabetically in `lib.zig`.
